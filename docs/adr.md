# Architecture Decision Records

## 2026-09-22 — Issue #200: Request the Directory property explicitly from the solution query

- Context: While verifying the brokered-service audience fix above on the real Stable/Insiders/Canary installs, the tool window failed to initialize with `ContextRelay window initialization failed: Data is not available for property 'Directory'. Refresh the query to retrieve data.`, which in turn left the panel stuck on "Not signed in" because `StartDeferredSignedInUserResolution` is only reached after initialization succeeds. `ContextRelayVsServices.GetWorkspaceRootsAsync` queried solutions with `QuerySolutionAsync(solution => solution, cancellationToken)`, an identity projection that does not request any properties; `Microsoft.VisualStudio.ProjectSystem.Query.ISolutionSnapshot.Directory` is populated on demand only and throws when read without being requested through `With()`. This is unrelated to the brokered-service audience change; it is a pre-existing defect that this session's cold-start ordering happened to surface.
- Decision: Change the query to `solution.With(s => s.Directory)` so `Directory` is included in the returned snapshot, per `AsyncQueryableExtensions.With<TEntity>(IAsyncQueryable<TEntity>, Expression<Func<TEntity, object>>)` ("Include a specific property in the query result").
- Reason: This is the SDK-documented way to request a property from an `IAsyncQueryable` projection; no other property on `ISolutionSnapshot` is read by this method, so no further properties need to be requested.
- Consequence: `GetWorkspaceRootsAsync` no longer throws when a solution is queried, so tool window initialization (and by extension deferred sign-in resolution) can proceed on cold start regardless of whether a solution was already loaded when a prior query happened to populate `Directory` as a side effect.

## 2026-09-22 — Issue #200: Proffer the UI language brokered service to PublicSdk as well as Local

- Context: Issue #192 proffered `ContextRelay.VisualStudioLanguage (1.0)` with `Audience = ServiceAudience.Local` only. In practice, `auto` UI language always resolved to English regardless of the Visual Studio display language, even though Tools > Options > ContextRelay (which reads the shell locale directly, in-process) localized correctly on the same instance. `GlobalBrokeredServiceContainer` ServiceHub logs (`%LOCALAPPDATA%\Temp\VSLogs\*.GlobalBrokeredServiceContainer.*.svclog`) from two separate devenv sessions showed the request declined: `Request for "ContextRelay.VisualStudioLanguage (1.0)" from Local, PublicSdk denied because the service is only exposed Local.` / `Remote request ... is declined: ServiceAudienceMismatch.` The out-of-process VisualStudio.Extensibility tool window requests brokered services as `Local, PublicSdk`, not `Local` alone, so the Local-only proffer from #192 was never reachable from that client, and `VisualStudioUiLanguageProvider` fell back to English every time a null proxy came back — treated as retryable, but the underlying cause (audience mismatch) is permanent, not transient.
- Decision: Change the `[ProvideBrokeredService]` audience to `ServiceAudience.Local | ServiceAudience.PublicSdk`. No change to `VisualStudioLanguageService.ResolveLanguage`, the provider's caching/cooldown logic, or Options localization (which does not use the broker). Added `InProcPackageVsixPackagingTests.BuiltVsix_BrokeredServiceAudienceIncludesPublicSdk`, which reads the packaged pkgdef's `BrokeredServices` entry from the built VSIX and asserts both the `Local` (0x3) and `PublicSdk` (0x10000000) bits are set, verified by mutation (reverting to `Local` alone fails the test with a message naming the cause).
- Reason: This does not contradict the #192 decision to keep the host language out of shared user settings and to resolve it per session — it only widens who may call the existing read-only, single-LCID-value service, which carries no meaningful exposure since it has no side effects and returns no user data.
- Consequence: Any Visual Studio process (not just this extension's own out-of-process host) can now query the LCID this service reports. The regression test guards against silently narrowing the audience back to `Local` in a future change.

## 2026-09-22 — chore/packageupdate: Select the Microsoft.Testing.Platform runner for `dotnet test`

- Context: Updating `xunit.v3` from 3.2.2 to 4.0.1 (and `xunit.runner.visualstudio` to 4.0.0) switched the test project's dependency graph from `xunit.v3.mtp-v1` to `xunit.v3.mtp-v2`, which pulls in `Microsoft.Testing.Platform` 2.4.0. That version's `Microsoft.Testing.Platform.MSBuild` targets raise a hard build error ("Testing with VSTest target is no longer supported by Microsoft.Testing.Platform on .NET 10 SDK and later") whenever `dotnet test` runs under a .NET 10+ SDK without opting into the new native `dotnet test` mode, so `dotnet test` failed before executing a single test on both the local machine (.NET 11 SDK) and CI (`windows-latest`, which resolves a .NET 10+ SDK because the repository had no `global.json`).
- Decision: Add a repository-root `global.json` that selects `"test": { "runner": "Microsoft.Testing.Platform" }`, keep `Microsoft.NET.Test.Sdk` (it still supplies `<OutputType>Exe</OutputType>`, which `xunit.v3.core.mtp-v2` now requires), and replace `coverlet.collector` (a VSTest data collector, inert under MTP) with `coverlet.MTP` 10.0.1. The test project now also declares `<OutputType>Exe</OutputType>` explicitly, instead of relying solely on `Microsoft.NET.Test.Sdk`'s targets to set it, so the executable contract is visible in the project file itself and does not silently depend on which SDK-provided package happens to be referenced. `.github/workflows/ci.yml` and `release.yml` now also install the .NET 10.x SDK alongside 8.0.x, and `ci.yml`'s `Test core` step uses the MTP CLI options (`--report-xunit-trx`, `--coverlet --coverlet-output-format cobertura`) in place of the VSTest ones (`--logger trx`, `--collect:"XPlat Code Coverage"`); the Codecov glob was widened to `coverage.cobertura*.xml` because `coverlet.MTP` appends a timestamp to the output file name. All of the above — `global.json`, the test project, and both workflow files — land together in this commit.
- Reason: All 318 existing tests passed unchanged once `dotnet test` ran in MTP mode (`DOTNET_TEST_RUNNER=Microsoft.Testing.Platform dotnet test ...`), confirming the failure was purely a test-runner selection problem, not a test-code or product-code regression. Migrating to MSTest was considered and rejected: MSTest 4.x is built on the same MTP v2 foundation and would require the identical `global.json` opt-in, so it would not avoid this change, while adding the cost of rewriting every test's attributes and assertions.
- Consequence: Running `dotnet test` locally now requires the .NET 10 SDK or later. Generated coverage files carry a timestamp in their name instead of a fixed `coverage.cobertura.xml`. `release.yml`'s `Test core` step needed no argument changes because it only passes build-related `dotnet test` options. CI no longer hits the VSTest error, since `ci.yml` and `release.yml` are updated in the same commit as `global.json`.

## 2026-09-22 — Issue #192: Follow the Visual Studio UI locale in automatic mode

- Context: The user confirmed that automatic language selection must follow the Visual Studio display language. The extension process culture can instead follow Windows and produce Japanese UI inside English Visual Studio.
- Decision: The existing in-process package obtains the UI locale from the Visual Studio shell and exposes it through a local-session brokered service. The out-of-process tool window resolves the language before creating its view model. Explicit English/Japanese choices remain immediate; unsupported or unavailable host languages fall back to English. Options use the same shell locale. The host language is not persisted in shared user settings.
- Reason: This implements the user-confirmed language contract and supersedes the process-culture limitation recorded for Issue #191. A session-local service keeps concurrently running Visual Studio instances independent.
- Follow-up: In the Experimental Instance a saved explicit `ja` kept the tool window Japanese, and the free-text `auto`/`en`/`ja` field hid that choice. The Options UI language property is now a fixed drop-down of the supported languages (Auto, English, Japanese); stored values are unchanged.
- Verification: Cover English/Japanese host locales, unsupported and unavailable locales, opposing process cultures, explicit overrides, initial labels, broker registration, and packaged resources. Verify the actual tool window in Visual Studio.

## 2026-09-21 — Issue #191: Localize command and menu names from the Visual Studio language pack

- Context: A build step replaced every `%ContextRelay.*%` display token in `extension.json` with English text, because some Visual Studio channels showed unresolved tokens literally. That made the Tools > ContextRelay menu impossible to localize, and the Japanese resource file existed for one command only.
- Decision: Keep every display token in `extension.json` and define all 15 in both `.vsextension/string-resources.json` (English, the fallback) and `.vsextension/ja/string-resources.json`. Visual Studio resolves them by its own UI language, meaning the installed and selected language pack, so the menu follows the Visual Studio language rather than the operating system language, and any other language falls back to English. The replacement patch is removed. The `ValidateContextRelayMenuMetadata` build task fails the build unless the manifest tokens, the default resource keys, and the Japanese resource keys are one identical set, checked both in the build output and on the copies packaged inside the VSIX.
- Reason: The user switches the Visual Studio language pack, not the operating system language, and expects the menu to follow it. Only token resolution by Visual Studio can do that.
- Consequence: On a Visual Studio channel that does not resolve the metadata, the menu shows raw tokens. This is verified in the Experimental Instance before release, and restoring a per-token English fallback would give up localization, so it needs an explicit decision. The tool window language is a separate setting: `UiLanguage` = `auto` follows the culture of the extension process, which is not guaranteed to match the Visual Studio language pack, so an explicit choice remains available.

## 2026-09-19 — Issue #184: Ground explicit-context chat requests and disable web context

- Context: Plain chat and `/ask` share one payload builder, and the same explicit context (pinned snippets, queued attachments, `#file` mentions, active editor) can now reach both routes. Copilot could still answer from web results instead of the attached material.
- Decision: When a request carries explicit context, append `ChatContextPayloadBuilder.GroundingInstructionText` to the outbound message and set `CopilotWebContext.IsWebEnabled` to `false` for that request. Requests without explicit context are sent unchanged, with no grounding instruction and no web context override.
- Reason: Attached files and pinned snippets are the reason the user attached them, so they must be the primary sources; turning off web context for grounded requests keeps the answer inside the material the user chose to share.
- Consequence: Grounded prompts differ from the literal user input, so history normalization and diagnostics operate on the composed request message. Documentation must state that a grounded request does not use Copilot web results. The `/ask` context check runs before the Copilot token is acquired, so a request with no explicit context is rejected without authentication, and trusted workspace roots are compared through their final directory targets so a redirected directory cannot widen the trusted set.

## 2026-09-15 — Issue #184: Align Visual Studio `/ask` settings with VS Code

- Context: The Visual Studio extension must apply the same explicit-context rules as the VS Code extension while retaining one shared settings file for all hosts.
- Decision: Persist `ChatMaxAttachedFiles` (default `5`, clamped to a non-negative value), `ChatAttachActiveEditor` (default `false`), and `ChatStreamResponses` (default `true`) in the existing settings object. `/ask` uses bounded pinned, pending-file, and optionally saved active-editor context and is rejected when no usable explicit context exists; plain chat remains context-optional. A submitted request claims its included pending attachments atomically and removes them from the visible pending queue before generation starts.
- Reason: A single additive JSON contract lets existing settings files continue to load while making the `/ask` behavior and user controls consistent across editors.
- Consequence: The Options page exposes the three Chat settings, and callers must honor the persisted attachment limit and streaming preference when constructing `/ask` requests. Files added during generation remain queued for the next request without sharing the limit with attachments already in flight.

## 2026-08-02 — Issue #164: Synchronize Remote UI suggestion selection by index

- Context: Binding the Remote UI `ListBox.SelectedItem` to a suggestion object updated the extension-side selection but did not reliably activate the WPF container's `IsSelected` state because object-reference identity is not guaranteed across the Remote UI boundary.
- Decision: Expose the selected suggestion's visible scalar index through the serialized ViewModel contract and bind it one-way to `ListBox.SelectedIndex`. Keep the existing suggestion object and keyboard command behavior for applying commands and help text.
- Reason: The selected container must enter `IsSelected` for the dynamic Visual Studio selection background and foreground triggers to render.
- Consequence: This intentionally changes the original implementation constraint that the ViewModel would remain untouched, but does not change the public extension API or keyboard assignments.

## 2026-08-02 — Issue #164 (follow-up): Replace `Selector.SelectedIndex` with a per-item `IsSelected` DataTrigger

- Context: The `SelectedIndex` fix above did not resolve the reported symptom — pressing Up/Down in the suggestion popup still did not visibly highlight a row. Root cause: `VisibleCommandSuggestions` is reassigned to a brand-new array on every keystroke (`UpdateVisibleCommandSuggestions`), and WPF's `Selector` resets `SelectedIndex` to `-1` via `SetCurrentValue` whenever `ItemsSource` is replaced. `SetCurrentValue` only overrides the effective value, not the data-bound base value, so a `Mode=OneWay` binding that later pushes the same index again is a no-op (WPF only re-evaluates on a *changed* source value) and the `-1` from the reset sticks. `ListBoxItem.IsSelected` therefore never turns `true`, so the `FluentListBoxItemStyle` `IsSelected` trigger never fires.
- Decision: Stop relying on `Selector` selection entirely for the popup. `SlashCommandSuggestion` now derives from `NotifyPropertyChangedObject` and exposes a serialized `IsSelected` bool that the ViewModel toggles directly when `SelectedCommandSuggestion` changes. The XAML `DataTemplate` for each suggestion row uses a `DataTrigger` on `IsSelected` to paint the selected background/foreground, instead of `ListBox.SelectedIndex`/`ListBoxItem.IsSelected`.
- Reason: A `DataTrigger` reacts to the bound data value directly and is immune to `Selector`'s implicit selection reset on `ItemsSource` replacement, and to any Remote UI ordering/timing between collection and scalar property updates.
- Consequence: `SelectedVisibleCommandSuggestionIndex` and `CalculateVisibleSelectionIndex` were removed as unnecessary. Keyboard movement (`MoveCommandSelection`), the visible scroll window (`CalculateVisibleWindowStart`), and command bindings are unchanged. This supersedes the "expose a scalar `SelectedIndex`" approach from the previous entry; the underlying invariant in `.agents/skills/wpf-fluent-vs-extension-ui/SKILL.md` has been updated to prefer per-item `IsSelected` state over `Selector.SelectedIndex` for Remote UI suggestion lists.

## 2026-08-02 — Issue #164 (second follow-up): Always reassign `VisibleCommandSuggestions` on selection change

- Context: The `IsSelected` `DataTrigger` fix above still did not visibly highlight the keyboard-selected row when confirmed against a real Visual Studio experimental instance. Root cause: `SelectCommandSuggestion(int index)` only called `UpdateVisibleCommandSuggestions()` (which reassigns `VisibleCommandSuggestions` to a new array and raises its change notification) when the visible scroll window needed to move. For most Up/Down presses — selection moving within the same 4-item window — `VisibleCommandSuggestions` itself was never reassigned; only the `IsSelected` property on the already-sent `SlashCommandSuggestion` item objects was mutated in place. This relies on Remote UI forwarding a `PropertyChanged` notification for an object nested inside a collection that was already sent to the Visual Studio process, a path this extension had never previously exercised (every other bound collection in `ContextRelayWindowViewModel` is always replaced wholesale, never mutated in place) and which did not visibly work in practice.
- Decision: `SelectCommandSuggestion` now unconditionally calls `UpdateVisibleCommandSuggestions()` after changing the selection, regardless of whether the scroll window moved. `IsSelected` stamping was centralized into a new `internal static ApplySelectionFlag(IReadOnlyList<SlashCommandSuggestion> window, SlashCommandSuggestion? selected)` helper, called from `UpdateVisibleCommandSuggestions()` immediately before the freshly built window array is assigned to `VisibleCommandSuggestions`. The redundant per-item toggling was removed from the `SelectedCommandSuggestion` setter.
- Reason: Reassigning the whole `VisibleCommandSuggestions` collection on every selection change reuses the one collection-update pattern already proven to work throughout this view model (`ChatHistory`, `SearchResults`, `Snippets`, and this same collection on window-scroll or on typing), instead of depending on unproven in-place item-mutation notification across the Remote UI boundary.
- Consequence: A small amount of extra Remote UI traffic on every Up/Down key press (the visible window, at most 4 items, is always resent instead of only on scroll). `ApplySelectionFlag` is unit-testable via reflection the same way `CalculateVisibleWindowStart` already is.

## 2026-08-02 — Issue #164 (third follow-up): Rebuild suggestion display items instead of reusing transmitted instances

- Context: The always-reassign fix above still did not visibly highlight the keyboard-selected row. Root cause: `UpdateVisibleCommandSuggestions` created a new *array* on every selection change, but the array still contained the same `SlashCommandSuggestion` instances that had already been transmitted to the Visual Studio process. Remote UI tracks previously sent objects by identity and does not re-serialize the current property values of an already-known instance, so the in-place `IsSelected` mutations performed by `ApplySelectionFlag` never reached the rendered rows — while the *initial* render (items freshly constructed with the flag already set) repainted correctly, confirming the `DataTrigger` mechanism itself works. Every collection that renders reliably in this view model (`ChatHistory`, `SearchResults`, `Snippets`) constructs brand-new item objects on every assignment.
- Decision: `UpdateVisibleCommandSuggestions` now builds the visible window from brand-new display clones via `SlashCommandSuggestion.CreateDisplayClone(source, isSelected)` (selection state baked in at construction) through a new reflection-testable helper `ContextRelayWindowViewModel.BuildVisibleWindow(suggestions, windowStart, maxVisibleCount, selected)`. Each clone's `ApplyCommand` is wired to commit the corresponding *master* suggestion so selection bookkeeping (`IndexOf` over `commandSuggestions`) keeps operating on canonical instances. `ApplySelectionFlag` was removed; master items are never flagged at all, which also eliminates stale `IsSelected` state outside the visible window.
- Reason: Constructing fresh item instances per update is the only collection-update pattern proven to repaint across the Remote UI boundary in this codebase; identity-based de-duplication makes any reuse of transmitted instances invisible to the UI regardless of collection reassignment.
- Consequence: At most 4 new `SlashCommandSuggestion` objects plus their `AsyncCommand` instances are serialized per Up/Down key press. The XAML `DataTrigger` on `IsSelected` is unchanged. This supersedes the second follow-up's in-place stamping; the invariant in `.agents/skills/wpf-fluent-vs-extension-ui/SKILL.md` was extended to require newly constructed item objects, not just a reassigned collection.
